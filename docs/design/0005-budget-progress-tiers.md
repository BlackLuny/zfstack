# 预算分级与推进保证（zfc #664）

## 1. 问题

global→port→peer 三层物理额度是共享池：adapter TX 队列、core TX 块、发送记录、出口包、连接状态、空闲 TX 缓存都从同一份额度取。已复现的死锁是：16 条流的 adapter TX 队列（各 64KiB）占满 819KiB 端口份额，core 需要一块新 64KiB TX 块才能接走这些字节，而 adapter 字节只有进 core 才会释放——没有任何释放能发生，等待者永远不被唤醒。空闲 TX 缓存同理：它占着 global/port 额度，不属于任何连接，不会自己释放。

## 2. 分级

每次物理申请带一个推进等级。等级越靠前，越是"让已缓冲字节往出口走"；越靠后，越是"接纳新字节/新状态"。

| 等级 | 申请 | 释放条件 |
|---|---|---|
| P0 出口 | 宿主出口包（zfc TCP/UDP 回程 `EgressPacket`） | 宿主发出即释放，不再申请任何额度 |
| P1 排空元数据 | 发送记录扩容；adapter RX 描述符扩容 | ACK / 应用读取（只依赖 P0） |
| P2 搬入 core | core TX 块（含缓存块改归属） | 数据被 ACK（依赖 P1、P0） |
| P3 准入 | 活跃连接状态、stream 状态、无状态回复、TIME_WAIT 槽、未标注的申请 | —— |
| P4 大块 | adapter TX 块与描述符、core RX/OOO | —— |

在每一层（global、port、peer）上，等级 k 的申请只在 `used + bytes ≤ limit − H_k` 时成功：

```
H_0 = 0
H_1 = R_egress                 出口包预留，只增不减：默认 8KiB；zfc 抬到 2×max(MTU, 2048)
H_2 = H_1 + R_meta             max(最小发送记录扩容, 最小 RX 描述符扩容)
H_3 = H_2 + R_block            TX_BLOCK_CHARGE
H_4 = H_3 + R_admit            ADMIT_BURST(4) × (core 连接状态 + adapter stream 状态)
```

P4 与 P3 分开，是为了繁忙端口仍能接纳一部分新连接：adapter TX、core RX/OOO 这些新字节只能用到 `limit − H_4`，留出 `R_admit` 给新连接的状态。真机 v3（尚未拆出 P4）上，adapter 队列会占满准入额度，后到的连接只能靠 SYN 重传排队，完成时间明显分成两批；拆出 P4 后这一现象消失。P3 和 P4 的租约合计仍不超过 `limit − H_3`，§3 的推进论证不变。

这一拆分**不保证准入不饥饿**。core TX 块是 P2，可以用到 `limit − H_2`，越过 P3 的上限 `limit − H_3`。既有连接持续发送时，TX 块会把这一层钉在 P3 上限之上，新连接的状态申请（P3）在整个传输期间都失败，SYN 被一直丢弃，直到客户端放弃。真机 4MiB 份额、单 peer 64 流三轮中，共 70/192 条连接在 SYN 阶段约 130 秒后失败，同期 `fail_active_state` 每轮 197–237 次，而已建立的连接全部完成、0 RST。准入状态不能提到 P2 之前，否则 §3 的链条会被准入状态截断。受压时怎样给新连接腾出空间见 §8。

预留大小取自各级单次申请的实际最小需求，不固定比例。

出口预留的实际值：zfc 一个 TCP 出口包最多计费 2×max(MTU, 2048)（池化缓冲最多保留目标容量的两倍），常见 MTU 下为 4KiB。zfc 在创建全局预算时按出口网卡 MTU 调用一次 `ensure_egress_reserve`，每个端口再按自己的内层 MTU 调用一次；两者取最大值，并且不低于库默认的 8KiB。所以 MTU ≤ 4096 时实际预留为 8KiB，可容纳两个出口包。出口网卡 MTU 是所有端口内层 MTU 的上界，因此预留在创建后不会再变大，已按旧值计算的端口下限不会失效。

某层 `limit < 2·H_4` 时，该层放不下"预留 + 正常准入"，预留在该层关闭，快照报告 `progress_reserve=false`。库本身不替宿主改额度，但在关闭状态下 §3 的推进论证不成立，因此宿主必须避开这种状态。peer 份额按端口份额计算，且至少包含一条完整单流（远大于 `2·H_4`）；全局预算最小 8MiB，也远大于 `2·H_4`。会落到下限以下的只有端口份额：8MiB 全局预算、1% 端口份额时约为 82KiB，而 `2·H_4` 约为 196KiB。

zfc 目前的处理是把端口份额抬到 `2·H_4` 并告警。这**改变了端口份额的上限语义**：配置值不再是该端口实际能占用的上限，受影响端口可以比配置多占约 114KiB，挤占同一全局预算下其他端口的余量。物理内存仍受全局硬上限约束，不会越界。要保持"配置即上限"，另一种做法是拒绝低于下限的配置（启动时报错、端口不建）。两者之间怎么选，属于产品决策，尚未拍板。

## 3. 推进论证

设连接 X 的 P2 申请（≤ R_block）在某层失败，则该层 `used > limit − H_3`。P3 与 P4 的用量合计最多到 `limit − H_3`（每次 P3/P4 申请成功时，总用量都不超过 `limit − H_3`），所以这一层必有等级 ≤ P2 的租约。任取一个属于连接 Y 的租约：它的释放依赖 Y 的 P1/P0 申请；若 Y 的 P1 失败，同理该层必有等级 ≤ P1 的租约……链条终止于 P0，而 P0 由宿主无条件排空。每次释放都按既有规则唤醒放得下的等待者。所以只要宿主在排出口，全局至少有一条连接能完成 adapter → core → 出口。

链条对三层分别成立：Y 的租约可能在别的端口或 peer，只要它占用的是同一层的额度就参与推进。连接状态属于 P3，不能吃掉推进预留。

缓存块不属于任何连接，是链条里唯一不会自己释放的租约，所以 §4 必须让它在受阻时变成释放。

实际申请可能大于预留。预留只覆盖每一级"最小的一次推进申请"；更大的申请（发送记录翻倍扩容、RX 描述符翻倍扩容）失败时，必须有不申请也能推进的办法：

- 发送记录：记录只在累计 ACK 时释放槽位，而丢包重传是累计 ACK 前进的前提。所以记录满、又需要重传时，扩容失败不能挡住重传：core 改为原地重传不超过一个 MSS 的丢失记录，复用它原来的槽位，不插入新记录；新数据、TLP 探测和拆分记录则等待槽位（`Conn::plan_in_place`）。被阻塞的连接只要有待重传的丢失字节，shard 仍会调度它。记录全部确认后 backing 会被释放，下次需要时申请最小容量，这一申请在 P1 预留之内。
- adapter RX 描述符：队列满说明已有 chunk 在等应用读取，应用每读一个就空出一个槽位，不需要扩容；队列读空后 backing 被释放，下一次只申请最小容量（在 P1 预留之内）。
- TX 块：pump 每次最多写 64KiB。core TX 为空时 head 回到 0，只需要一块新块，正好是 `R_block`。
- 例外：MTU 变小后，比新 MSS 长的丢失记录必须先拆分，拆分需要新槽位。它只能等别处释放，本变更不处理这种情况。
- adapter stream 状态：握手完成后 adapter 才接管连接；如果此时再按准入等级申请 stream 状态，一旦失败只能复位这条已建立的连接。真机上 idle 缓存和繁忙的 adapter 队列占满准入额度时，11/16 条新连接就是这样在 25ms 内收到 RST。现在改为在 SYN 准入时，与 core 连接状态一起预留 stream 状态（`Shard::reserve_stream_state`）。租约保存在连接的 `Conn` 里，accept 时交给 adapter。额度不足就丢 SYN，由对端重传；如果额度只是被本 shard 的空闲缓存占着，先就地回收再重试一次。stream 状态的内存照常计费，生命周期不变。

不保证：准入不饥饿（见 §2，由 §8 处理）；公平性（等待者按 FIFO 唤醒，但没有吞吐下限）；远端零窗口或宿主停止排出口（由 orphan/超时处理，不属于预算死锁）。

## 4. 压力下的缓存回收

- 任意 `MemoryHandle` 申请失败且全局缓存非空时，发出回收请求：推进全局回收 epoch，唤醒登记过的缓存持有者（每个 driver 一个）。
- shard 在每轮 `run` 开头比较 epoch，有新请求就丢弃本 shard 全部空闲块。丢块会真实释放 `Box<[u8]>` 与租约，并照常唤醒等待者。
- 缓存块仍然占 global/port 额度（真实驻留），只是不再无限期占着。受压期间块会在"释放入池 → 下次失败被回收"之间周转，这里用少量分配成本换取推进。

## 5. 物理上界

分级只收紧各层上限，不放宽；硬上限 `high`、port、peer 限额不变。adapter 与 core 同时持有同一批字节的两份拷贝时，两份各自计费，不做额度转移。缓存回收释放的是真实内存。宿主出口包的分配器取整部分仍按现状尽力补计，不在本变更范围内。

## 6. 诊断

每端口快照新增以下内容，用于在真机上判断卡在哪一步：

- 按等级和按层（global/port/peer）的申请失败计数；按用途细分：adapter TX、adapter RX、stream 状态、TX 块、发送记录、出口、准入。
- 当前等待：`adapter_wait_core`（adapter 等 TX 块）、`record_wait`（core 等发送记录）、按用途统计的物理等待者数；zfc 侧另报出口内存等待与出口队列满，两者分开计数。
- 缓存回收次数与字节数。
- 连接关闭原因（normal/reset/timeout/aborted），以及 adapter 主动 abort 的原因（stream 状态申请失败、描述符分配失败、orphan 超时）。

## 7. 验收

- `adapter_queues_do_not_starve_core_tx_blocks` 转绿。
- 记录满且整窗丢失时仍能原地重传：`full_send_records_retransmit_in_place_when_growth_is_impossible`（去掉该修复后，传输停滞约 25 秒）。
- zfc 最小合法份额保留预留：`smallest_legal_port_share_keeps_the_progress_reserve`。
- 准入额度不足时，已建立的连接不被复位：`established_connection_is_not_reset_when_stream_state_is_short`（去掉预留后测试失败）。
- 缓存阻塞的确定性回归：缓存占满端口后 P3 申请失败并发出回收请求；shard 回收后等待者被唤醒，申请成功。关闭回收时该测试必须失败。
- 分级边界的单测覆盖三层。
- 端到端覆盖：多 peer（peer 份额小于端口）、多端口共享受限全局预算、同一端口连续多轮"压满 → 撤压 → 新单流"。全程采样断言 `reserved ≤ high`、port/peer 用量 ≤ 限额。
- 出口计费测试保留，但它不能证明出口循环等待已排除；真机复跑三组场景，并记录 RST 来源。

## 8. 未解决：受压时的新连接准入

见 §2。已拍板的方向是：内存紧张时按连接限制缓冲，让既有连接让出额度，给新连接的状态腾出空间，行为上接近内核在内存压力下收紧每连接缓冲的做法。设计与验收另文给出；在此之前，份额被既有连接占满时新连接会在 SYN 阶段被拒绝。
