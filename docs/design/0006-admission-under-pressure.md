# 受压时的新连接准入（zfc #664，0005 §8）

## 1. 问题

0005 的分级保证"至少一条连接能推进"，但不保证新连接能进来。core TX 块是 P2，上限 `limit − H_2`，比准入线 `limit − H_3` 高出一个 TX 块。既有连接持续发送时，每释放一块就会被下一次 P2 申请拿走，用量一直停在准入线之上，新连接的状态申请（P3）每次都失败，SYN 被丢到客户端放弃。真机 4MiB 份额、单 peer 64 流时，三轮共 70/192 条连接因此失败。

本地红测 `new_connection_is_admitted_while_senders_keep_refilling_tx_blocks`：819KiB 份额，一个任务模拟繁忙发送端，每释放一块 TX 块就在同一步里申请回来，让端口一直停在准入线之上，持续 3.5 秒。新连接的 SYN 在 0、1、3 秒三次被丢，7 秒才进来（3/3 次复现）。

用真实慢速读取流做负载的版本不稳定：本地回环排空太快，准入线附近时有时无空隙，16 流 6 次中 5 次复现，24 流反而全部通过。所以红测改为直接模拟"释放即回填"。

## 2. 做法：准入欠账

内核在内存压力下收紧每个 socket 的发送缓冲，连接状态本身不进 `tcp_mem` 计费，所以新连接总能进来。这里连接状态和缓冲共用同一份额度，只收紧缓冲不够：让出的额度会立刻被下一次缓冲申请拿走。因此让准入失败在这一层留下欠账，由欠账挡住缓冲回填，直到新连接进来。

- **记账**：新连接的状态申请（core 连接状态 + adapter stream 状态）失败时，shard 在拒绝它的那一层记一笔欠账，金额是这条连接需要的全部状态字节数。每层欠账合计不超过 `R_admit`（ADMIT_BURST 条连接的状态）。欠账是一个 RAII 凭据（`AdmitDebt`），放在 shard 的待准入表里（按四元组，最多 ADMIT_BURST 条）。同一 SYN 重传只刷新期限，不重复记账。
- **跟随拒绝层**：同一连接的重传如果被另一层拒绝（例如首次是 global，之后 global 腾出空间，变成 port 或 peer），欠账迁到新的拒绝层，旧层的欠账立即还清。
- **期限跟随 SYN 退避**：SYN 重传按指数退避（Linux 为 0、1、3、7、15、31、63s），到下一次重传的间隔约等于距首次被拒的时长。期限取 `max(4s, 2 × 距首次被拒 + 2s)`，上限 64s。4s 下限覆盖初始 RTO 为 3s 的客户端。这样连续多次失败时，欠账仍能保留到下一次重传。
- **不再释放就撤销**：欠账依赖这一层的 TX 块和发送记录随 ACK 释放。若该层连续 1s 没有释放任何这类字节（持有者对端零窗口、宿主停止排出口等），欠账腾不出空间，只会挡住其他发送端，于是撤销欠账（条目保留）；下一次重传仍被拒时重新记账。
- **还账**：这条连接之后准入成功，就把凭据从表里删掉；期限到了对端还没重传，也删掉。凭据析构时扣回欠账并唤醒物理等待者。期限按拒绝它的那个 shard 自己的时钟计算：core 不读时钟，各 driver 的时间零点也不同，不能用一个跨端口的全局时间。shard 的 `next_deadline` 包含最早的到期时间，所以空闲时也会按时醒来。
- TIME_WAIT 槽申请失败不记欠账：它失败的原因可能是连接数上限，而不是内存。
- **欠账期间的上限**（每层独立，`D > 0` 时）：
  - P4 大块：余量从 `H_4` 加到 `H_4 + D`。
  - P2 TX 块：余量从 `H_2` 加到 `H_2 + min(R_block + D, drain)`。`drain` 是该层 TX 块与发送记录的租约字节数，也就是 ACK 能直接释放的部分；空闲缓存块不算。加上 `R_block` 是因为 P2 平时可以比准入线高出一块。
  - 欠账期间，释放的 TX 块不进空闲缓存，直接归还额度。
  - P0/P1/P3 不变。
- **效果**：欠账期间，P2 和 P4 回填后用量不超过 `limit − H_3 − D`。既有块随 ACK 释放后，这段余量留给准入；客户端下一次 SYN 重传即可进来。准入成功后欠账还清，上限恢复。

## 3. 推进论证不变

设连接 X 的 P2 申请在欠账期间失败：

- 若 `min(R_block + D, drain) = 0`，上限与 0005 相同，沿用 0005 §3 的论证。
- 否则 `drain > 0`：这一层存在 TX 块或发送记录。它们随 ACK 释放，释放前最多只需要 P1/P0 申请（原地重传、出口包），而 P1/P0 不受欠账影响。所以链条照常终止于出口。

P4 更严格了，P3+P4 ≤ `limit − H_3` 仍然成立。欠账只收紧上限，不放宽，所以物理上界不变。

## 4. 代价与边界

- 欠账期间，这一层会闲置最多 `R_block + D`（约 64KiB + 几 KiB）不给缓冲使用，直到新连接进来或期限到期。客户端放弃时，最长闲置 64s（期限上限）。
- 每条被拒的连接仍要多等一次 SYN 重传（首次约 1s），因为第一次失败时额度还没腾出来。
- 连接状态本身占满份额时（空闲连接太多），欠账腾不出空间，新连接照样被拒。这属于连接数超出份额，不在本变更范围内。
- 按连接的公平上限不在本变更范围。已知的相关缺口是零窗口连接独占份额（见 0005 §3 的"不保证"），与欠账无关：本地实验中，没有任何欠账时同样会发生。

## 5. 诊断

快照新增 `admission_debt`（global/port/peer 当前欠账字节数，peer 为本端口各 peer 之和）。shard 统计新增：`admission_debts`（因内存被拒而登记的连接数）、`admission_debts_expired`（到期未重传）、`admission_debts_moved`（迁到另一层）、`admission_debts_stalled`（因该层不再释放而撤销）。zfc diag 行对应输出 `admit_debt_global/port/peer`、`admit_debts`、`admit_debts_expired`、`admit_debts_moved`、`admit_debts_stalled`。

## 6. 验收

本地（已通过）：

- `new_connection_is_admitted_while_senders_keep_refilling_tx_blocks` 转绿：握手在 2.5s 内完成（修复前 7.0s，3/3）。去掉欠账对上限的影响后，测试重新失败。
- `refused_syn_leaves_an_admission_debt_until_admitted`：拒绝后记账；同层重传只刷新；欠账期间释放的块不被拿回；重传准入后还清。
- `admission_debt_follows_the_level_that_refused_the_retransmit`：首次被 port 拒、重传被 peer 拒时，欠账迁到 peer，之后准入成功。去掉迁移后失败。
- `admission_debt_outlasts_backed_off_retransmits`：0、1、3、7s 四次都被拒（期间该层持续释放，空间被发送记录占回），在 3、7、15s 重传前欠账都还在，15s 进来。固定 3s 期限时失败。
- `admission_debt_is_lifted_when_the_level_stops_releasing`：持有者不释放时，1s 后撤销欠账，其他发送端恢复申请；对端不重传则按期限到期。去掉撤销后失败。
- `owed_admission_room_does_not_stop_established_streams`：6 条真实流以 128KiB/s 读取，另有任务模拟回填，端口越过准入线后再发起新连接。在新连接被拒、欠账生效的窗口里，每条旧流都至少读到 64KiB，新连接 2.5s 内握手，全部传完，无 RST（5/5 稳定）。
- 单测：`admission_debt_holds_back_tx_blocks_and_bulk_at_every_level`（三层分别覆盖 P2 与 P4 收紧、P1/P3 不受影响、还账后恢复），`admission_debt_never_holds_back_a_level_without_tx_blocks_or_records`（`drain = 0` 时 P2 不受影响；去掉 `min(drain)` 后失败），`admission_debt_is_capped_and_its_repayment_wakes_waiters`。
- 0005 的全部测试保持通过（共 114 项）。

真机（worker 218，候选 v5，2026-09-27，证据在 zfc `tasks/zfstack-664-rerun/evidence/`）：

- 4MiB 份额、单 peer、64 流三轮：负载 192/192，中途新连接 12/12，均在 1.16–1.19s 内握手（一次 SYN 重传）并传完。以 5 秒采样，未观察到任何一条流（含新连接）停滞。0 RST、0 abort；撤压后单流 3/3。修复前的 v4 在同一场景只完成 122/192。
- 819KiB 单 peer 16 流三轮：48/48 + 6/6，握手 1.04–3.06s。4 peer × 2 流三轮：24/24 + 6/6。默认预算 16/64 流各两轮：160/160 + 12/12。以上全部 0 RST。
- 欠账没有到期，没有因不再释放而撤销，也没有迁层。说明真机上欠账都在下一次重传时被还清。
- CPU A/B：两个候选只差本改动，基线、构建参数和诊断行都相同，默认预算下按 A B B A A B 交替跑。
  - 64 流：peer 份额占满，A、B 没有可测差异，B/A = 0.989，两组区间重叠。
  - 16 流：没有内存压力，B 的 CPU/GiB 稳定高约 4.3%。
  - 进程内基准（无压力、同一段测试代码）：没有测到欠账代码的开销，B/A = 0.983。本机上 zfstack 自身约 0.7 CPU s/GiB，节点进程约 42 CPU s/GiB，欠账代码不足以贡献 1.8 s/GiB。
  - 节点上 16 流约 4% 的差异未归因，可能来自整个二进制的代码布局，未证实。由 zfc #682 跟踪。
- 同一 A/B 中，默认预算 64 流的新连接握手：A 为 10–36s（第 1 槽未被拒），B 为 5.6–8.5s。两个版本都有个别流 10–15s 无进展，与欠账无关。
