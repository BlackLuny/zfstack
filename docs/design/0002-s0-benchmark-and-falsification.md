## 1. 要证伪的假设

| 编号 | 假设 | 成立意味着 |
|---|---|---|
| H1 | 80 ms 浅瓶颈的差距主要来自没有 pacing 导致的突发丢包，而 pacing 开不起来是因为唤醒迟到时信用处理不当 | 在 fork 上做 EDT + 按实测间隔定信用上限即可改善 |

## 2. 台架

### 2.1 netem 台架（修正版）

**v0.1 的问题**：计划在同一个 netem 上同时做 `delay D` 和 `limit L`，并按 `L = 0.25 × BDP` 设置浅队列。
但 netem 的 `limit` 限制的是 qdisc 持有的全部包，**包括正在经历模拟传播时延的包**。以 200 Mbps、RTT 80 ms 为例：单向 40 ms 传播中的数据就有约 1 MB，
而 0.25 × BDP 只有约 0.5 MB。按原设计，连维持目标速率所需的在途数据都放不下，测到的丢包是台架造成的，不是瓶颈队列造成的。

**修正后的拓扑**（三个 namespace，时延和瓶颈放在不同的 qdisc 上）：

```
 ns client                       ns router                                   宿主（zf-worker）
 ┌──────────────┐  vc ⇄ vr1  ┌────────────────────────────────────┐  vr2 ⇄ vh  ┌───────────────────────┐
 │ 内核 wg      │────────────│ vr1 出方向（下行瓶颈）:              │────────────│ WG 入站端口            │
 │ iperf3 client│            │   htb rate R → bfifo limit Lq 字节   │            │ netstack（被测）        │
 └──────────────┘            │ vr2 出方向（上行瓶颈）: 同上         │            │ iperf3 server（lo）     │
   vc 出方向：netem delay D   └────────────────────────────────────┘            └───────────────────────┘
   （上行传播时延，limit 足够大）                                               vh 出方向：netem delay D + loss p
                                                                                （下行传播时延与丢包，limit 足够大）
```

- **传播时延**：netem 放在两端的出方向，`limit ≥ 2 × R × D / MTU`，再加 50% 余量，保证它本身永不丢包。
- **随机丢包**：放在下行的 netem 上（上行需要时对称配置）。
- **瓶颈队列**：放在 router namespace 里，`htb rate R` 下挂 `bfifo limit Lq`，`Lq = k × R × RTT`，k = 2（深）或 0.25（浅）。只有这里会因为排队而丢包。
- **速率口径**：R 按外层 WG/UDP 报文计。WG 每包约增加 60–80 B 开销，报告里同时给出外层速率和内层 TCP 有效速率。
- **关闭 offload**：所有 veth 执行 `ethtool -K <dev> gso off gro off tso off`。避免 GSO 超大包让 htb/netem 的计数和整形失真（netem 文档对此有专门提醒）。
- **计数归零**：内联 counter 的 reset 不生效，每一格运行前都删除并重建 qdisc。

基础脚本仍然用 zfc `tasks/wg-netstack-perf/netem_matrix.py`，在它上面改成这个拓扑。

### 2.2 E0：台架校准（任何 TCP 实验之前必须先通过）

用恒定速率的 UDP 流（`iperf3 -u -b`，走 WG 隧道）逐项检查，每个 RTT × 队列组合都要过一遍：

| 检查 | 方法 | 通过条件 |
|---|---|---|
| 时延 | 空载 ping | 实测 RTT 与配置值偏差 ≤ 5% |
| 无意外丢包 | 以 0.9 R 发送，丢包率配置为 0 | 端到端丢包 < 0.01%，所有 qdisc 的丢包计数均为 0 |
| 瓶颈位置 | 以 1.2 R 发送 | 丢包全部发生在 router 的 bfifo 上；netem 的丢包数为 0 |
| 队列容量 | 以 1.2 R 发送时的 RTT 增量 | 约等于 `Lq / R`，偏差 ≤ 10% |
| 配置丢包率 | 以 0.5 R 发送，配置丢包 p | 实测丢包在 p 的 ±10% 以内 |

有任何一项不通过，就先修台架，不跑后续实验。校准结果与每次实验结果一起归档。

### 2.3 真机 WAN 台架（确认用）

95（客户端，内核 WG）↔ 218 / 96（worker），不加 netem。只跑关键格，确认 netem 上的结论在真实链路上也成立。

### 2.4 节点与带宽

- 227（2 核）与 96（1 核），对比核数的影响。
- 瓶颈速率 200 Mbps；2 核节点加测 500 Mbps，观察 CPU 成为瓶颈时的表现。
- **同机注意**：客户端、iperf3 服务端、netem 和 worker 共用一台机器的 CPU。压测端争用 vCPU 会被误判为协议栈的差异，所以在 1 核节点上
  只跑单流和 8 流，并按 §3 的口径分组件统计 CPU；256 流只在 2 核节点上跑。

## 3. 统计与 CPU 口径

- 每格 5 次重复，每次 30 s，丢弃前 3 s。报告中位数与 bootstrap 95% 置信区间，并保留每秒序列（用来暴露 stall）。
- 比较两组时，只有置信区间不重叠且差异 ≥ 5% 才判为有差异。
- **CPU 分母用有效字节**：接收端应用实际收到的字节，不含重传。否则重传越多，CPU/GB 反而越好看。
- **CPU 分组件统计**：worker 进程、客户端（wg + iperf3 client）、iperf3 server、softirq（netem/htb 所在）分开。整机口径只在和内核后端比较时使用。
- 每次运行都记录：内核版本、节点、zf-worker 的 commit、smoltcp fork 的 commit、qdisc 配置与计数、E0 校准结果。

## 4. 实验

### E1 基线矩阵

- 对照：smoltcp（fork main `9e68a37`；端口 CC 用 BBR 和 CUBIC 各一组）、kernel-TUN、原生内核 WG。
- 第一批（必跑）：流数 1 与 8，下行，RTT 1/12/80/200 × 丢包 0/0.1/1/2%/突发 × 深/浅队列。
- 第二批：上行；256 流（仅 2 核节点，RTT 12/80 × 丢包 0/1%）。
- 产出：每格吞吐、重传率、零吞吐秒数、瓶颈丢包数、CPU/有效 GB。

### E2 全链路时间线（H2）

在 zfc 的临时分支上，给 netstack 路径加抽样打点（1/1000），记录一个出包的四个时刻：

```
t0 计划发送时间（pacing 算出的 next_send_time；没有 pacing 时为数据可发的时刻）
t1 netstack 循环实际运行到这条连接的时刻
t2 包进入 from_stack 通道 / sink 的时刻
t3 加密完成、交给 sendmmsg 的时刻
```

另外记录每次唤醒的间隔，以及进程的 `/proc/<pid>/schedstat`（运行队列等待时间）和整机 steal。

在空闲、单流 200 Mbps 下行、8 流 + 256 空闲连接三种负载下，分别在 1 核和 2 核节点上采样。

判读：
- t1 − t0 大，且 schedstat 的运行队列等待也大 → 线程拿不到 CPU（steal 或其他线程抢占）。
- t1 − t0 大，但运行队列等待小 → 同一个 runtime 里其他任务的长轮次在前面（H2 成立）。
- t3 − t2 大 → 瓶颈在出包段（交回 Tokio 任务加密），这正是驱动 B 必须覆盖加密发包的原因。

v0.1 的两个 500 µs 探针方案作废：探针本身会增加唤醒负载，也无法区分 Tokio 时间粒度、线程调度、CPU 配额限流和 steal 这几种原因。

### E3-sim pacing 算法的确定性仿真（H1 的前置）

先不碰网络，也不碰 fork，用一个独立的小仿真（Rust 单文件或 Python）验证 pacing 算法本身会不会限死吞吐：

- 输入：目标速率 200 Mbps 与 1 Gbps；执行间隔 G = 1 / 2 / 5 / 10 ms，外加 E2 实测的间隔分布。
- 被测算法：v0.2 的「量子 + 2 量子 backlog」；v0.3 的「信用上限 = 实测间隔 P99，夹在 2–10 ms」。
- 输出：实际均速、单次最大突发字节、最大突发折算成的排队时延。

预期（用于检验仿真本身是否正确）：v0.2 算法在 G = 5 ms、200 Mbps 下均速约 80 Mbps；v0.3 算法在 G ≤ 10 ms 时均速等于目标速率，G = 5 ms 时单次突发约 125 KB。

### E3 fork 上的 pacing 实验（H1）

在 fork 分支 `s0-edt` 上实现 0001 §7.2 的 pacing（只改发送调度）：

| 变体 | pacing | 唤醒与出包 |
|---|---|---|
| E3-0 | 关（现状） | Tokio，出包交回 WG 任务 |
| E3-a | EDT，信用上限跟随实测间隔 | 同上 |
| E3-b | 同 E3-a | **netstack 循环与加密 + sendmmsg 一起挪到独立线程**（zfc 临时分支：该线程持有 UDP socket 的 fd 克隆，对 peer 的 `Mutex<Tunn>` 加锁调用 `encapsulate`） |

- 运行的格：RTT 12/80 × 丢包 0/1/2% × 深/浅队列 × 流数 1/8，下行。
- 指标：吞吐、重传率、瓶颈 bfifo 丢包数、RTT 增量，以及出包节奏（在 router 的 vr1 上抓包头，统计 1 ms 窗口内的最大字节数）。
- E3-b 的判定依据是**线上出包节奏确实改善，且 CPU/有效 GB 不退化**，而不是 E2 打点里 t1 − t0 变小。

判读：E3-a 或 E3-b 把 80 ms 浅瓶颈拉到内核的 80% 以上，则 H1 成立。

### E4 接收侧主动窗口更新（H3）

fork 分支 `s0-rwnd`：应用读走数据后，可通告窗口增长 ≥ 2 × MSS 就立即发窗口更新。
跑上行单流，RTT 12/80，丢包 0%。客户端抓包头，统计 window-limited 与 zero-window 的时长。

### E5 恢复路径剖析（H4）

不写代码。用 E1 中 1%/2% 丢包各格的数据，加上 `WGDIAG` 已有的计数（`rtos/frtx/sackrtx/partrtx/rescan/reneg`）与客户端抓包，统计：
每次丢包的恢复时长、走 RTO 的恢复次数占比、伪重传比例。和 kernel-TUN 同格对照。

### E6 连接规模（H5）

单个 200 Mbps 下行流 + N 个空闲连接（N = 0 / 1k / 10k）。测该流的吞吐、worker CPU/有效 GB、RSS，
用 `perf record` 统计 `Interface::poll` 及其子调用的占比。

### E7 并发建连（H6）

并发 64 / 256，共 5000 个连接（`connbench.py`）。记录成功率、建连延迟 P50/P99，失败按超时/RST 分类，对照 kernel-TUN。
另外把 zfc 的 `PENDING_LISTENER_TTL_MS` 和 listener 池上限调大，再跑一组，看调参能否消除失败。

### E8 混合负载延迟基线（为 G-lat 建立基线）

一个下行大流跑满瓶颈，同时每 100 ms 做一次 1 KB 请求 / 1 KB 响应（自写 echo，走同一个 WG 隧道，不同连接）。
记录小请求的 P50/P99/P99.9 往返时间，和空载时的差值。smoltcp、kernel-TUN 各跑一遍，RTT 12/80 × 深/浅队列。
这一组不用来证伪任何假设，只作为 0001 §15 G-lat 的基线。

## 5. 决策表

| 实测结果 | 决策 |
|---|---|
| H1 成立，且 H4/H5/H6 均不成立 | **暂停 zfstack**，把 E3（及 E4，如果成立）回灌 fork，关闭 #639 相应条目 |
| H1 成立，H4 或 H5 也成立 | 先回灌 E3/E4 止血；**zfstack 进入 S1** |
| H1 不成立，H4/H5 成立 | **zfstack 进入 S1**；E2 的结论用于决定驱动默认值 |
| H1–H5 都不成立 | 差距来源不明，先补充取证（perf + 逐包对比内核），不进入 S1 |
| H6 能靠 zfc 调参消除 | 在 zfc 单独修（另开 issue），不计入自研理由 |

无论走哪一行，**回灌 E3/E4 之后的 fork 都作为「改良版 smoltcp」**，在修正后的台架上重跑 E1 的第一批与 E8，
结果就是 0001 §15 中 G-perf、G-lat、G-cpu 的比较基线。

## 8. 注意事项

- 节点使用走 zfc-test 流程（节点锁、测试端口前缀、结束后自动清理）。
- 跑 E1 前确认 zf-worker 包含 #637 的修复（fork `9e68a37`），并记录 commit。
- #637 的经验：一次塌陷会留下持续数分钟的残留会话。每次运行之间重置 iperf3 和 socket，用 `ss` 确认没有残留。
- 开发机的 TUN 代理不放行 UDP，WG 客户端必须放在测试节点上。
- #639 的 59/178 数据来自旧台架，不直接作为 S0 基线；S0 在修正后的台架上重测。
