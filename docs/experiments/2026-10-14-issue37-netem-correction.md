# Issue #37：netem 队列丢包更正

来源：[issue #37 的实机诊断与更正评论](https://github.com/BlackLuny/zfstack/issues/37#issuecomment-6159317526)。已核对评论正文；以下是测试执行者在 rig 218 发布的结果，未在当前云环境重新运行，完整逐次原始日志仍由执行者保存。

## 撤回的归因

此前把 256 流 + 50 ms 下的吞吐下降及 >3 s 停顿归因于 zfstack 的结论不成立。`run-rig.sh` 给客户端 `wg0` 配置 `netem delay 50ms`，未指定包上限，默认 1000 包队列丢弃了大量下载 ACK。c1323fa 的一次测量为丢弃 570155 包、成功发送 627156 包；ef92e54 为丢弃 527542 包、成功发送 619810 包。队列上限改为 100000 后，执行者报告 12 次延迟运行均零 qdisc 丢包、零 >3 s 超时流。

停顿流快照显示重传/RTO：cwnd 为 5152，rto_count 从 3 增至 6，rto_us 退避至 4387627，后续快照 lost 等于 tx_queued。远端窗口仍非零；core TX 接近份额上限，want_write 已置位，等待 ACK 腾空间。这些快照支持 TCP 丢包恢复，不能作为 relay 漏唤醒的实机证据。

## 修正台架后的对照

相同 100000 包队列，每臂两次、交错运行；下表为 256 流 + 50 ms 上行延迟。

| 版本 | 吞吐 Mbps | CPU s/GiB | >3 s 超时流 |
|---|---:|---:|---:|
| ref `37c016d` | 1048 / 864 | 15.0 / 17.6 | 0 |
| base `579b7c3` | 1260 / 1290 | 11.9 / 11.7 | 0 |
| `ef92e54` | 1413 / 1411 | 10.9 / 10.8 | 0 |
| `c1323fa` | 1413 / 1397 | 10.8 / 11.1 | 0 |

ref 的同端口轻 peer 两次仍超时，因此不能把 ref 描述为整体通过；原因未继续调查。无附加延迟的 256 流吞吐依次为 ref 1211/1163、base 1509/1497、ef92e54 1616/1587、c1323fa 1580/1594 Mbps，没有 >3 s 超时，但 ref 第二次有一条零字节流。

base 在修正台架上高于 ref，不支持此前“50 ms 下吞吐下降 28%–44%”的结论。两种候选相对 base 的均值吞吐约增加 10%，CPU/GiB 约降低 7%–8%；c1323fa 与 ef92e54 的吞吐差小于 1%，这些重复中未观察到明确差异，不代表统计等价证明。

1500 空闲连接准入与 netem 无关：#39 / `579b7c3` 已修好，后续两个候选也均为 1500/1500。环形 TX 和两处 relay 等待缺口的确定性回归证据继续成立；后两者不再被用来解释这批实机停顿。广播唤醒优化不纳入本次修改。

## 台架防回归

- `L2_NETEM_LIMIT_PACKETS` 显式配置队列包上限，默认 100000，在暂停 watcher 前校验。
- 负载前后保留所有四个客户端 `tc -j -s` 和 `tc -s` 快照，结果携带累计计数及测量增量；中断退出时尽量补 post 快照后再销毁拓扑。
- 仅加延迟的实验出现 qdisc 丢包、缺失/无效统计、计数器重置或配置变更，结果判为台架失败。比较器对两臂都检查，并拒绝包上限不同的对照；旧延迟报告缺少统计时不假定零丢包。

验证命令：

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s harness/l2 -p 'test_*.py' -v
bash -n harness/l2/run-rig.sh
git diff --check
```

17 项 Python 测试通过，包含丢包、缺失/无效计数、计数器重置、qdisc 配置变化、基线污染、两臂上限不一致，以及启动前参数拒绝；shell 语法与 diff 检查通过。本次只改台架、比较器和证据文档，未更改 c1323fa 的 Rust 生产代码。当前环境拒绝 `unshare -n`，无法创建测试网络命名空间；没有把 Python 计数器回归测试描述为真实 WireGuard 复测。
