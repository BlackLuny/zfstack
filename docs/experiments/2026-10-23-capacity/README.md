# 发送容量、预取与高负载公平性的复核

源码基线 `9d6fb7684e3842da16e673825d3c9ace724aa433`。本轮没有修改
`src/` 或生产默认配置；增加了基准参数、冻结的实验脚本和原始证据。
同一 release 二进制比较所有候选，SHA-256：
`226064630d182124194d55f8fa348cc6aada676ef85031d41d88e78be8c0d724`。

## 目前可以支持的判断

**不能把“统一缩小缓冲”当作高负载公平性的通用优化。**
256 KiB 总 TX 上限在本机 TUN **8 流**下载中有 CPU/内存收益信号，
但在 80 ms RTT 的服务器单流上导致约 73% 吞吐损失，在本机 TUN
单连接补测中也损失约 18.3% 峰值吞吐、增加约 21.5% CPU/GB。
200 条大连接场景下也没有改善平均用户延迟。因此不将它作为 server 或 client 默认值。

**64 KiB 预取上限的明显公平性收益没有在独立确认中复现。**
200 条大连接的两对筛选样本曾出现尾延迟改善信号，但更长的 12 对新样本中，
平均用户延迟变化 -1.55%，最差用户 P99 -0.11%，区间均包含改善与退化。
不能把最初的 -33% P99 当成可交付收益。加上少连接补测，共 92 次运行全部通过校验。
本轮没有找到同时满足明显公平性收益、CPU 目标和少连接峰值保护的默认参数改法。

真实 VPS 入口拥塞仍应优先研究源站 TCP 的聚合背压与按用户分配读额度。
ZFC 已有 #684 的目标 socket 接收缓冲开关，不需要从零增加一个相似开关；
缺少的是跨同一用户多条连接的聚合约束，以及它对真实入口队列的效果验证。
[入口控制设计](UPSTREAM-DESIGN.md) 已定位源码、现有能力与下一轮证伪条件，
该设计尚未实现，本轮 TUN 数字不是它的性能结果。

下一步优先级如下；“候选”不代表已经形成满足全部目标的帕累托改进。

| 方向 | 依据与用途 | 还缺什么证据 |
|---|---|---|
| 按用户限制源站 TCP 聚合积压/读额度 | 对应真机入口拥塞；可用有界 peer 状态、复用队列换取批量调度 | 跨连接身份、窗口/缓冲总账、真实入口延迟与固定负载 CPU |
| 256 KiB 总 TX 上限 | 8 流下有收益，但本轮已观察到少连接明显回退 | 不推广默认；若研究条件启用，须证明竞争判定、进入/退出转换及少连接性能 |
| 按字节的 peer 公平服务和有界 driver 工作量 | 可能改善异构 MSS、CPU 忙时的服务份额 | 需要单独原型；不能用旧的“pump 限字节后立即回队”反例作为实现 |
| 紧内存下按活动用户重新分配进展额度 | 少量受预算约束的预留可防止某用户长期拿不到资源 | 逐用户无进展观测、取消/退出回收、吞吐与额外状态成本 |

增加大 FIFO 不在建议之列。额外内存优先用于有界、可复用的调度状态和
最小进展资源，避免把它全部变成更深的排队。

用户追加的约束是：**连接较少时尽量保留极限单连接吞吐。** 因而后续的公平性
原型应在有竞争或持续积压时介入，在空闲/少连接时保留原批量路径并借用空闲份额。
不能把连接数本身等同于拥塞，也不能用 CPU 或内存收益抵偿明显的单连接限速。
为补足本机 TUN 候选只有 8 流数据的缺口，另冻结了
[1/2 流峰值对照](LOW-CONCURRENCY.md)，与原 80 次结果分别分析。

## 第一阶段：56 次筛选

详细预注册规则见 [PROTOCOL.md](PROTOCOL.md)，复现入口见
[bench/capacity](../../../bench/capacity/README.md)。

四格：本机 TUN 8 流下载/上传、CUBIC 200 heavy + 3 light 的 100 Mbps / 10 ms
FIFO 链路、单 heavy + 3 light 的 100 Mbps / 80 ms 高 BDP 对照。
每格 A/A 后执行 B、C、D 各一个 ABBA 块，候选块顺序冻结后随机排列。
每候选每格只有两对，以下为两对百分比变化的中位数，**不是置信区间**。

- A：原配置。

- C：仅 `prefetch_max=65536`，不降低原在途上限。

## 为什么不直接改默认值

1. **本机 TUN 的收益不能外推到 WAN。** B 的下载 CPU/GB 降低同时伴随
   吞吐上升，CPU/s 约 +1.11%；尚未证明固定有效负载下 CPU 降低。
   追加少连接补测后，client profile 也不能统一采用该值；详见下节。
2. **小在途窗口的低延迟不符合本次目标。** 80 ms 组的 B/D 吞吐约从
   95 Mbps 降到 25 Mbps，远超允许的小幅损失。相应 CPU/s 降低主要是少做了工作。
   `256 KiB × 8 / 80 ms ≈ 26.2 Mbps` 的窗口上限也与这个限速量级一致。
   队列上限为 2 MB，原基线有明显排队；并非 80 ms 的传播延迟可以被配置消除。
3. **预取也不是已经证实的免费优化。** 上传 C/D 触发了预注册的 -3% 筛除线，
   但样本少，上传还是方向负对照，机制归因未成立；不能将这组结果称为已定位的上传缺陷。
4. **不能绕过已有噪声。** 高 RTT 组 A/A goodput 变化 -9.97%、CPU/GB -14.68%；
   200-heavy 组 A/A 最差用户 P99 +24.55%。筛选中的个位数百分比无法直接定性。

## 独立确认

规则见 [CONFIRMATION.md](CONFIRMATION.md)：同一二进制，12 个新的配对，
AB/BA 各六对、事先随机排列，每次 20 秒/4 秒 warmup，每用户 400 个加载请求。
主指标为等权用户平均延迟，最差用户 P99 为次指标；不合并筛选数据，不替换失败样本。

24/24 次有效，12 对完整；32400 个计划请求（含空闲基线）全部完成，
到达时间、独立原始样本、deadline、配置和二进制身份校验全部通过。
所有配对和各次结果保存在 [confirmation-summary.json](confirmation-summary.json)。

| 指标 | 配对变化中位数 | 配对 bootstrap 95% 区间 |
|---|---:|---:|
| bulk goodput | +0.004% | [-0.019%, +0.015%] |
| 栈线程 CPU/GB | -1.125% | [-1.920%, +1.239%] |
| 栈线程 CPU/s | -1.155% | [-1.895%, +1.252%] |
| 生命周期峰值 RSS | +0.520% | [-0.202%, +1.703%] |
| 等权用户平均延迟（主指标） | -1.546% | [-7.633%, +8.136%] |
| 最差用户 P99（次指标） | -0.110% | [-29.012%, +41.352%] |

该场景没有达到预先定义的至少 20% 平均延迟改善；CPU 区间也仍允许小幅回退。
吞吐保持稳定并不足以构成整体优化。A/C 各自运行的用户平均延迟中位数
为 36.54/36.34 ms，最差用户 P99 中位数为 145.13/144.07 ms；
这些未配对的绝对值只帮助理解量级，表中结论使用逐对变化。

该结果支持保持当前预取默认值，不能证明此参数在所有其他负载下都无效。
源码中的预取最小值本来就是 64 KiB；在每连接速率较低时，新上限可能并不
改变实际容量。这是与结果相符的解释，尚未通过逐连接预取分布遥测建立因果归因。

## 追加的少连接峰值保护

[LOW-CONCURRENCY.md](LOW-CONCURRENCY.md) 在补测前冻结。
对本机 TUN 下载的 1/2 条连接分别执行 A/A + ABBA，20 秒/4 秒 warmup，
其余参数与原 client 场景一致；使用相同 Rust 二进制及最终已核验的容器启动配方。
12/12 次通过，配置/源码身份审计通过，记录的整秒无进展和 cgroup throttling 均为零。

| 连接数 | 256 KiB 相对原配置的 goodput | 代理 CPU/GB | 峰值 RSS | 两对 goodput 变化 |
|---|---:|---:|---:|---|
| 1 | -18.26% | +21.48% | -30.84% | -17.17%、-19.35% |
| 2 | -3.39% | +2.51% | -44.55% | -1.10%、-5.68% |

单连接 A/A goodput 变化为 +2.70%，两连接为 +1.13%。这里只有两对，不能精确
资格化 1–3% 的差异；但单连接的两次明显回退已足以拒绝该配置作为客户端默认值。
两连接的回退幅度仍需区分噪声与机制，不影响单连接保护的否决结论。

这也说明仅有“8 流 CPU/GB 降低”不足以满足本次目标。后续公平性机制应保留
无竞争时的原发送窗口和批处理，仅在竞争/持续积压时启用约束，并验证退出后
恢复峰值。不得把一个固定小窗口或一个连接数阈值直接当成已验证的自适应策略。
完整逐次/逐对结果见 [low-concurrency-summary.json](low-concurrency-summary.json)。

## 验证、环境与证据边界

- Rust 1.94.1，release，fat LTO，单 codegen unit，panic abort，锁定依赖；
  21 项 Rust 基准单元测试与 3 项 Python 证据测试通过。
- 第一阶段冻结的 49 个源码/配置文件、所有命令、运行次序与二进制身份审计通过；
  确认和少连接阶段各核对 52 个文件。每次运行均保留命令、环境、原始输出、资源与 cgroup 计数。
- 共享云执行器：Linux 6.18.55、x86_64、4 CPU quota、允许 5 CPU；
  测量使用 0–3。容器独立网络、无 host networking，构建在测量前完成。
  没有物理 CPU 隔离、频率控制、PMU 或裸机性能保证。
- 三个阶段 cgroup CPU throttling 增量均为零；这不排除宿主 steal、频率变化
  和调度噪声。全机 CPU 计数仅作诊断，不能作为此服务 CPU 指标。
- 旧 #29 的裸机结果、#69 的本地队列原型、被关闭的 #895 和本轮结果均分别记录。
  本轮不包含真实 WG/VPS 入口实验，也不验证聚合读额度设计。

原始数据、冻结方案、构建日志、审计脚本与源码快照见 [evidence.tar.gz](evidence.tar.gz)，
摘要见 [screening-summary.json](screening-summary.json) 与
[confirmation-summary.json](confirmation-summary.json)、

复核原始二进制身份的完整审计还需要保留的测量二进制，归档未包含可执行文件。
