# 高负载用户公平性：入口控制的下一步设计

状态：根据现有源码与已发表实验整理的设计，**尚未实现或实测**。
本目录的容量实验只测试 zfstack 的发送配置，不是本设计的验证。

## 为什么优先研究入口

[zfstack #69 最后的拆主机实验](https://github.com/BlackLuny/zfstack/issues/69#issuecomment-6312651702)
在纯内核 TCP 下也复现了秒级轻用户延迟：20 Mbps worker 的入口被
target → worker → client 大下载占满；只占 worker 出口时没有同样的退化。
两组不同运营商的客户端均受影响。该结果将这组真机故障的主要位置指向
worker 之前的入口/运营商队列，不能据此认定所有部署的队列都在同一位置。

因此，zfstack 接收到数据后再公平发送，不能消除数据到达之前的等待。
已有的本地瓶颈 peer DRR + pushout 仍是“控制真正瓶颈队列可改善公平性”的
证据，但没有证明在 worker 内增加同一队列能解决该真机问题。
[UDP 出口控制原型 #895 的最终记录](https://github.com/BlackLuny/zfstack/issues/69#issuecomment-6312269103)
还包含上传/混合方向回退，不能当成待直接合入的优化。

## 已有入口与尚缺的能力

ZFC 已合入 [#684](https://github.com/BlackLuny/zfc/issues/684)：
`ZFW_TCP_TARGET_RCVBUF_KB` 默认关闭，在连接目标的 TCP socket 上设置
`SO_RCVBUFFORCE`（失败则 `SO_RCVBUF`），随后设置 `TCP_WINDOW_CLAMP`。
它处理的是大量快源站 → 慢下游连接造成的内核 TCP 内存压力。
已有 2048 KiB 配置的双主机成功记录，但不能推出它解决了 #69 的入口公平性。

这些 SHA 是文件对象，不是整个仓库的提交 SHA；读取快照保存在实验原始证据中。
ZFC 的开关作用于返回的下一跳 socket；经过 SOCKS、Hammer、TOT 等中间链路时，
需要在真正连接源站的落地点施加控制，不能假定 worker 上一处设置就端到端有效。

现有开关还有四个边界：

1. **按连接而非用户**。2048 KiB × 200 条连接仍有很大的总窗口；
   Linux 接收缓冲记账通常约为请求值的两倍，且还存在额外 socket 开销。
2. **连接后设置**。不能撤回已经发布的接收窗口，也不能取消已在链路中的字节。
   连接前设置是否能减少冷启动突发，必须作为独立实验，验证 window scale 与吞吐。
3. **窗口不是速率**。仅缩小 socket 内存并不等价于把入口稳定控制在 97% 链路容量。
   不同源站 RTT、并发数和拥塞控制会改变效果。
4. **小窗口有 BDP 成本**。#684 已记录只锁缓冲却没有正确抬升 clamp 会严重限速；
   本目录也用高 RTT 对照排除了任意连接统一设置很小 TX 总上限的做法。

## 建议的最小可测原型

先利用已有开关和 relay 插入点做实验，暂不引入新的队列层或修改 TCP 协议。

### 计费单位与背压位置

- 使用经认证的 `(tenant, logical port, peer)`，由接受连接一路传到拨号与 relay。
  `remote_overlay` 本身不是足够的身份契约，不能临时用目标 IP 或连接 ID 代替用户。
- 每个入口链路有总预算，每个 peer 有份额；一个 peer 的所有目标连接共享份额。
  peer 内再轮转连接。多开连接不增加该用户的聚合额度。
- 优先在从目标 socket 读取的位置限额；与现有下游 send-space 背压组合。
  预算涵盖尚未交付的核心 TX、adapter/relay 数据及受控的内核接收缓冲。
  从 socket 搬到另一个用户态队列不算释放预算。
- 内核 socket 缓冲与远端已获窗口不能被精确当成一个用户态 credit 计数器。
  原型要分别记录已知占用、配置窗口上界和不可撤回的在途估计，公布总上界的缺口。
  必要时限制同一 peer 同时活跃的目标连接/拨号突发，且保留新请求的进展机会。

### 保留空闲容量，拥塞时才介入

- **少连接/单连接峰值吞吐优先保留。** 在没有用户竞争或持续积压时走原来的
  批量快速路径，允许借用空闲窗口与预算；不能为多用户公平性永久截小单流 BDP。
  连接数只是观测量，不能单独作为拥塞证据。验证退出拥塞后恢复单流性能，
  并覆盖 1/2/4 条连接、不同 RTT、丢包与 MTU 的峰值 goodput。
- 单用户/无竞争时借用空闲份额；用户加入后渐进收回借出的额度，禁止撤回已经发送的窗口。
- 以事件驱动的活动 peer 队列进行按字节轮转，累计小批量额度后读/splice。
  初始候选批量为 16–64 KiB，具体值由 CPU 与延迟对照决定。
- 为晚到的用户保留有界的小额启动/控制报文资源；在总资源不足时限制准入，
  不能许诺无限用户都得到固定最小窗口。长连接不能永远排在新短连接后面。
- 若需要把到达速率压在链路容量以下，使用聚合读速率控制作为独立因子，
  验证传递到 TCP 接收窗口后的效果。先测试已知限速的 97%/99%，
  再研究容量估计；不要把猜测的 RTT 增长当作可靠容量反馈。
- 有界状态复用优先于每包分配；仅在活动集合/预算变化时更新份额，
  唤醒只发生在无额度 → 有额度或无工作 → 有工作时。避免每包扫描所有连接、
  每包 `TCP_INFO`/`setsockopt`、固定毫秒轮询和仅 `yield_now` 后立即自唤醒。

### 需要保护的行为

ACK/FIN/RST、半关闭和重传不依赖应用 payload 的读额度；每个已准入 peer
有可观测的最大连续无进展时间。新连接、idle → burst、peer 退出、取消与错误
必须回收额度和唤醒正确等待者。下载控制不能拖慢上传或 ACK 通道。
短请求不能靠识别包内容获得特殊优先级；按身份和已占用资源实现公平。

这一原型可能用少量复用队列和 peer 状态换取更低的调度/唤醒开销，
但增加内存预算本身不会增加链路容量，也可能扩大排队，不能直接视作优化。

## 冻结下一轮验证的条件

采用拆主机拓扑：源站、限速 worker、bulk 客户端、独立 light 客户端。
先验证纯内核 TCP 对照可以重现入口拥塞；出口拥塞是另一独立场景。
记录每个位置的队列/丢包/重传，防止把瓶颈搬走误报为解决。

对照因子分别是原行为、已有静态 RCVBUF、同配置下 peer 聚合读额度、
聚合读速率控制及组合；每个因子单独解释。测试 1/16/64/200 条大连接、
多个重用户与晚到轻用户、CUBIC/BBR、异构 RTT/MSS、上传/下载/混合，
高 RTT 单流、紧内存、idle/reburst 与取消/半关闭。

固定到达率的轻请求应保留所有计划到达和超时，不只统计完成样本。
报告等权用户平均延迟、最差用户 P99、超时比例、每用户连续无进展时间，
以及每用户 goodput/Jain 指数；轻需求未饱和时不以所有用户带宽相等为目标。
对无限拥塞只承诺可验证的准入与服务条件，不能用一轮有限实验宣称绝不会饿死。

正式进入默认配置的目标：峰值 goodput 损失至多 1–3%，固定有效负载下的
服务 CPU 不回退且尽量下降，平均用户延迟与最差用户尾延迟明显改善，
超时和无进展事件不增加。预先约定实际 SLO 与统计精度，至少 12 对独立重复，
A/A 噪声或置信区间过大时保留未决；CPU 口径包括由机制引起的内核开销。

这部分需要 ZFC/private_tun 的运行路径与真实入口台架；本次只完成源码定位与
实验接口设计，没有把 zfstack 本地 TUN 筛选结果冒充该原型的实现或实测结果。
