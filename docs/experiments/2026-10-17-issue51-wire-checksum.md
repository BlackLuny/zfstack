## 2. 基线 (`9f424bf`) 反汇编根因与代码优化设计

1. **消除 `sum_bytes` 的 6 个被调用者保存寄存器压栈与内联阻塞**：
   - 基线 `sum_words_portable` 标注了 `#[inline(always)]`，在默认 `x86_64`（SSE2，无 SSE4.1 `pmovzxdq`）下未向量化，展开为占用 8 个通用寄存器的标量循环并内联进 `sum_bytes`，导致每次调用 `sum_bytes`（即使 `< 64B` 短头或走 AVX2 分支）入口都要 `push` 6 个被调用者保存寄存器（`%rbp, %r15, %r14, %r13, %r12, %rbx`），且 `sum_bytes` 体积达 `785 B`。
   - **优化方案**：`sum_bytes` 先处理 `0..3` 尾字节，再以尾调用位置调用 `#[inline(never)] fn sum_words(acc, &data[..words])`（跨调用零活跃变量，`sum_bytes` 自身**零 callee-saved 寄存器压栈**，符号体积缩减 **-66.8%**，`785 B -> 261 B`）。`< 64B` 短切片采用按位测试（`32/16/8/4`）的本机序 `u128` 累加（`sum_small_words`），避免分支预测失败与间接跳转表。

2. **AVX2 256B 混合端口循环（`sum_words_avx2`）**：
   - 基线 `sum_words_avx2` 每 32B 依赖两次 `vpmovzxdq`（全部压在 Intel 单一 Shuffle Port 5），且循环后使用 24 条指令的 `overflowing_add` 串行提取链。
   - **优化方案**：使用 4 个 `__m256i`（32 个 `u32` 通道），主循环按 **256B** 展开：前 64B 使用 `2 × vmovdqu + vpand + vpsrld $16`（分流至 Port 0/1），后 192B 使用 `12 × vpmovzxwd`（Port 5），同时降低稳态退休指令数（`65495B` 稳态指令数 `9,892 -> 9,568`，**-3.28%**）并解除 Port 5 单端口瓶颈；尾部按 `128/64/32/16/8/4` 位测试无循环收尾。
   - **分块不溢出证明**：每 `MAX_CHUNK = 262_144`（256 KiB）折叠一次；单块内归约到 `sum128`（4 个 `u32` 通道）时每通道最多累加 $32,768$ 个 `u16`（$\le 32,768 \times 65,535 = \text{0x7fff\_8000} < 2^{31}$），两半 64 位相加 `lo64 + hi64` 的低 32 位上限为 $\text{0xffff\_0000} < 2^{32}$，不会向高 32 位产生跨界进位；超过 256 KiB 的任意长度切片通过外层循环分块折叠。

3. **跨架构零溢出 8 通道 `u32 -> u64` 树状归约实现（`sum_words_portable`）**：
   - 初版 `[0u32; 16]` 顺序归约在 AArch64 上因 `u32` 溢出语义限制未能触发 NEON 向量化且产生了寄存器 spill。
   - **优化方案**：改为 8 通道 `[0u64; 8]` 累加 `u32::from_ne_bytes` 并采用结合律树状归约 `(lanes[0] + lanes[1]) + (lanes[2] + lanes[3])`。在三个目标下均实现**零 callee-saved GPR 压栈**与原生 SIMD 自动向量化：
     - `x86_64` 默认（SSE2）：自动向量化为 `movdqu + punpckldq/punpckhdq + paddq`（仅用 `xmm0..xmm7`）。
     - `x86_64` `-C target-cpu=native`（AVX2）：自动向量化为 128B 展开的 `vpmovzxdq ymm + vpaddq ymm`。
     - `aarch64`（Apple M1 Max / NEON）：自动向量化为 `ldp q + uaddw.2d/uaddw2.2d` 64B 展开循环（仅用 `v0..v5`）。

4. **寄存器内直接累加 IPv4 头校验和、`pseudo_sum` 与 TCP 头/选项（`parse_ip`、`emit`）**：
   - `parse_ip` 使用 `ipv4_header_checksum_ok` 在寄存器内完成 20B IPv4 头（及 `ihl > 20` 选项）累加与无分支 `fold_u64`。
   - `emit` 在单次 `match (p.src, p.dst)` 中同时完成 IPv4 头校验和与 `pseudo_sum`，写 `buf` 全程只写不读（消除基线写完 8/16-bit 字段后立即 32-bit 读回导致的两次 Store-to-Load Forwarding 停顿），在写 TCP 头与选项时直接累加 `tcp_sum`，并以 `debug_assert_eq!(i, tcp_hlen)` 移除死 `memset@PLT` 调用。

## 3. 深度检视问题逐项闭环说明（P1 / P2 / P3）

### 3.1 `P1a`：`sum_bytes_64B` 基线 421 条指令异常的根因与预热后稳态指令数
- **根因确认**：在 `base` 中，`sum_bytes_20B` 与 `sum_bytes_32B` 走 `< 64B` 分支，而 `sum_bytes_64B` 是进程内**首次进入 `data.len() >= 64` 分支并调用 `is_x86_feature_detected!("avx2")` 的用例**。首次调用触发了 Rust 标准库 `std_detect::detect::cache::detect_and_initialize`（执行 `cpuid` 并初始化全局原子缓存），一次性消耗了 **315 条动态指令**；随后执行的 `sum_bytes_512B` 直接命中已初始化的缓存，因此只有 204 条指令。
- **修复与复测**：在 [`count-ir-warm-script.txt`](./2026-10-17-issue51-wire-checksum/count-ir-warm-script.txt) 中对所有函数先执行 1 次预热调用完成 CPU feature 缓存初始化，再在完全相同的 `-C opt-level=3` 编译级别下测量单次调用的**稳态退休指令数**（详见 [`instruction-counts-warm-named.json`](./2026-10-17-issue51-wire-checksum/instruction-counts-warm-named.json) 与 [`instruction-counts-native-named.json`](./2026-10-17-issue51-wire-checksum/instruction-counts-native-named.json)）。预热后 `sum_bytes_64B` 稳态指令数为 **`123 -> 98`（`-20.33%`）**，`512B` 为 **`179 -> 166`（`-7.26%`）**，`1460B` 为 **`362 -> 306`（`-15.47%`）**，`65495B` 为 **`9,892 -> 9,568`（`-3.28%`）**，指令数随包长单调递增，所有软件校验和路径稳态指令数全面下降。

### 3.2 `P1b`：微基准 A/A 偏移消除与 TUN `soft_mtu1500_mixed8` 双峰分布根因
1. **微基准 A/A 对照偏移根因与修复**：
   - 初版微基准对 `base_lib`、`cand_lib`、`base_aa_lib` 共用了同一个间接调用闭包 `run_one(f: extern "C" fn(...))`，导致同一条 `call *%reg` 指令在三个目标地址之间切换，触发 CPU 间接分支预测器（ITTAGE）别名冲突与 64B 代码行对齐差异（如 `parse_ip_tcp_softcsum_52B` A/A 出现 `+3.48%` 偏移）。
   - 在 [`wire-microbench-harness.txt`](./2026-10-17-issue51-wire-checksum/wire-microbench-harness.txt) 中改为三个独立直接调用函数 + `-C llvm-args=-align-all-functions=6` 64B 函数对齐并绑定单核后，`parse_ip_tcp_softcsum_52B` 的 A/A 偏移降至 **`+0.50%` `[-0.12%, +1.32%]`（Native 下 `+0.03%`）**，`portable_64B` 降至 **`-1.02%` `[-2.34%, +0.17%]`（Native 下 `+0.10%`）**，所有 27 个用例的 A/A 95% CI 均包含 `0%` 或小于 `±1.1%`。
2. **TUN `soft_mtu1500_mixed8` 双峰分布（`~8.2 Gbps` vs `~3.2 Gbps`）根因与受控复测**：
   - 通过开启 `ZFBENCH_TX_CACHE_SAMPLE_MS=1000` 导出连接实时快照（`ZFBENCH_CONNECTIONS`），查明原矩阵命令中同时开启 `--driver-thread --splice` 时的双峰机制：
     - `bench/src/client.rs:384` 的 `test_mixed` 硬编码使用 **1 条 bulk 下载流**（`run_bulk(o, false, 1, ...)`），回环上游每次写入 `64 KiB`（`65,536 B = 45 × 1448 + 376 B`）。
     - 远端宿主机（Intel Core i7-1265U Alder Lake）包含物理 P-core 与 E-core。当 `--driver-thread` 将 `zfc-driver` 与上游线程分离在不同速度的 vCPU 上时：若上游写入快于 `zfc-driver`，发送缓冲保持 `tx_unsent > 0`（`small_segs = 0`），驱动连续批处理满 MSS 报文，吞吐达 `~7.5–8.5 Gbps`；若 `zfc-driver` 快于上游写入，每 `64 KiB` 均将 `tx_unsent` 抽干至 `0` 并产生 1 个 `376 B` 尾段（`small_segs > 4,500`），触发每秒约 1,500 次跨线程 `epoll_wait`/`eventfd` 休眠唤醒，吞吐落入 `~3.1–3.5 Gbps` 模态。
     - 此外，`bench/src/tunproxy.rs:572` 中 `--client-proxy zfstack-client` 在未开启 `--vnet-hdr` 时默认设置 `trust = o.client_profile && !vnet = true`（`RxChecksum::Trusted`），跳过了入站软件校验和验证。
   - **修复后受控测试**：在 [`run-tun-clean-script.txt`](./2026-10-17-issue51-wire-checksum/run-tun-clean-script.txt) 中改用 `--client-proxy zfstack`（无 `--vnet-hdr` 时 `RxChecksum::Verify` 全量校验 RX+TX 软件校验和）、不开启 `--driver-thread` 跨核竞争，并绑定在快核集合 `taskset -c 0,1,2` 上运行。`soft_mtu1500_mixed8` 在全部 6 轮（18 次运行）中彻底消除双峰跳变，稳定落在同一模态（基线中位数 `3.336 Gbps`，候选中位数 `3.319 Gbps`，AB 变化 `-2.74% [-4.91%, +4.99%]`，AA 对照 `+2.87% [-17.43%, +11.37%]`）。

### 3.3 `P2a` & `P2b`：跨架构（`aarch64`）与 `-C target-cpu=native` 性能闭环
- **`aarch64` (`Apple M1 Max`, `rustc 1.94.1`)**：全部 **27/27 项微基准 12/12 轮全胜**，耗时下降 **`-4.44% ~ -49.15%`**（其中 `portable_64B` **-45.27%**、`portable_512B` **-49.15%**、`portable_1460B` **-49.07%**、`emit_data_softcsum_1460B` **-43.67%**、`parse_ip_tcp_softcsum_1448B` **-18.44%**）；双端协议栈 `pareto_probe` 4 个场景 CPU/GB 下降 **`-1.92% ~ -3.81%`**。
