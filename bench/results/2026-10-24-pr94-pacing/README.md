# PR 94 更新后再测：接口聚合 pacing

PR 94 在 `17034b3` 之后不再只是测试队列。生产 core 增加了可关的接口聚合 pacing：多个 peer 同时有数据时，按配置速率出队；只有一个 peer 时走原来的批量路径。默认速率是 0，也就是关闭。这次在同一台 4 vCPU 机器上，用 main（`9d6fb76`）和这份新二进制对比。链路队列固定为 FIFO，所以这不是上一轮那个 bench peer 轮转。

打开时速率是瓶颈的 99%：`12,375,000` 字节/秒。瓶颈仍是 100 Mbps，双向随机丢包，测量窗口 8 秒。多用户是 25 Hz 开环、256 字节。217 次里 215 次通过正确性检查。失败的两次都是发生器漏了 1 到 3 个计划包，延迟样本仍在。

上一轮的 [peer 队列对比](../2026-10-23-pr94-cross/README.md) 还在。那次生产代码没有变。这次变了。

## 关着的时候，新二进制和 main 一样

80 ms、3 个轻用户、8 条重连接、无丢包，pacing 关闭：

| 二进制 | 吞吐 | 轻用户平均 | 最差 P99 | 栈 CPU s/GB | RSS |
|---|---:|---:|---:|---:|---:|
| main | 95.62 Mbps | 140.2 ms | 159.8 ms | 3.94 | 15.3 MiB |
| PR 94 关 | 95.85 Mbps | 139.9 ms | 159.7 ms | 3.92 | 15.5 MiB |
| PR 94 开 | 96.01 Mbps | 108.9 ms | 139.6 ms | 3.76 | 15.6 MiB |

单流下行也一样：80 ms 无丢包，main 两次 93.5 Mbps，PR 94 关 95.4 / 93.5，开 95.4 / 94.4。单 peer 快速路径没有把峰值打掉。这是 100 Mbps，不是 PR 里没通过 −3% 界限的那组数 Gbps 少连接峰值。

## 打开之后，延迟降多少取决于 RTT 和连接数

3 个轻用户、8 条重连接、CUBIC、无丢包。关是 PR 94 自己的关闭臂。

| RTT | 关：平均 / 最差 P99 | 开：平均 / 最差 P99 | 吞吐 关 → 开 |
|---:|---|---|---|
| 20 ms | 37.9 / 40 与 75.6 ms | 23.7 / 36.8 与 39.1 ms | 96.16 → 95.46 Mbps |
| 80 ms | 139.9 / 159.7 ms | 108.9 / 139.6 ms | 95.85 → 96.01 Mbps |
| 250 ms | 432.8 / 500.0 ms | 251.7 / 256.1 ms | 88.9 → 95.8 Mbps |

20 ms 的平均延迟从大约 38 ms 降到 23.7 ms。P99 的关闭臂有一次是 75.6 ms，不能把中位数 57.8 当成稳定基线；打开的两次是 36.8 和 39.1 ms，和 main 的 39.9 ms 齐平。

80 ms 是部分改善：平均 −22%，最差 P99 −13%，还停在 140 ms，没有贴到 80 ms 的 RTT。上一轮 bench peer 轮转在同一格能把 P99 收到 80.5 ms。生产 pacer 在 99% 速率下留了更多排队。

250 ms 是这轮最清楚的一格。两次打开都是平均 251.7 ms、P99 256 ms，也就是基线 RTT。吞吐从 87–91 Mbps（main 两次只有 81–82）升到 95.7–95.9 Mbps。栈 CPU 从 4.39 降到 3.66 s/GB。RSS 仍是 23 MiB。

生产 Tokio driver（不 splice）和 shard 路径同一方向：250 ms 平均 436 → 252 ms，P99 500 → 256 ms，吞吐 83.4 → 96.3 Mbps。

### 200 条重连接

这是 PR 正文那档负载。20 ms、无丢包、两次：

| | 吞吐 | 平均延迟 | 最差 P99 |
|---|---:|---:|---:|
| 关 | 96.10 / 96.11 Mbps | 42.4 / 43.8 ms | 119.9 / 119.7 ms |
| 开 | 95.51 / 95.59 Mbps | 25.0 / 25.0 ms | 39.9 / 39.3 ms |

平均大约 −42%，最差 P99 大约 −67%，吞吐 −0.6%。打开时记下 98.6 MB paced、3855 次 pause。80 ms、200 条、各一次：平均 162 → 116 ms，P99 320 → 154 ms，吞吐 94.0 → 96.8 Mbps。仍高于 80 ms RTT。PR 报告的是 Tokio splice、200 条、12 对上的 −57% 平均和 −82% P99。这里的 shard 路径方向相同，幅度小一些，而且 20 ms 的 P99 收到约 40 ms 后就不再往下。

### 用户数和重连接数

无丢包、pacing 开相对关：

- 轻用户 1 或 8、重连接 8：80 ms 平均从 141–146 ms 降到 98–99 ms。250 ms、8 个轻用户的平均降到 272 ms，但最差 P99 仍有 810 ms（关是 972 ms）。
- 只有 1 条重连接时改善更小。80 ms 平均 209 → 164 ms，P99 266 → 203 ms。250 ms 平均 429 → 383 ms，P99 仍是 429 ms。单条大象流不会把接口打进持续竞争。
- 32 条重连接、250 ms：平均 422 → 310 ms，P99 558 → 349 ms，吞吐 86.8 → 96.2 Mbps，栈 CPU 5.05 → 3.83 s/GB。

1% 双向丢包时，开和关缠在一起。80 ms、8 条重连接：吞吐 12.6 → 12.7 Mbps，平均 84.7 → 84.4 ms，P99 都是 201 ms。20 ms 和 250 ms 同样没有拉开。

BBR、80 ms、8 条重连接、无丢包：平均 108 → 90 ms，吞吐 92.6 → 95.1 Mbps，栈 CPU 6.44 → 4.80 s/GB，但最差 P99 236 → 273 ms，没有变好。1% 丢包时吞吐 88.5 → 82.5 Mbps。

轻用户之间的延迟 Jain 仍然约等于 1。pacing 减少的是轻用户排在重 peer 后面的时间，不是轻用户彼此的差距。

## 和其他栈

100 Mbps、FIFO、无丢包单流。zfstack 开和关都在这张表里。

| RTT | kernel-cubic | smoltcp-cubic | zfstack 关 | zfstack 开 |
|---:|---:|---:|---:|---:|
| 20 ms | 96.3 | 88.1 | 96.2 | 96.3 |
| 80 ms | 96.3 | 14.2 和 90.6 | 95.4 / 93.5 | 95.4 / 94.4 |
| 250 ms | 96.3 | 97.2 | 96.2 | 96.2 |

80 ms 的 smoltcp-cubic 两次差很大，不能收成一个中位数。kernel 和 zfstack 两次都在 93 Mbps 以上。单地址的 mixed 测试里，pacing 开和关的回显 P99 相同：20 ms 都是 40 ms，80 ms 都是 137–138 ms，250 ms 都是 429 ms。这条路径上的下载和回显不是两个 peer，pacer 不会把它们拆开。kernel 在 80 ms 的 mixed P99 是 135 ms，和 zfstack 接近。smoltcp-bbr 的 mixed P99 中位数是 1608 ms，同时吞吐只有 71 Mbps。

1% 丢包、80 ms、单流：kernel 1.5、smoltcp-cubic 2.1、zfstack 关和开都是 1.5 Mbps。丢包仍然比 pacing 更大。

栈 CPU 继续只算用户态栈线程。内核 TCP 的协议工作在软中断里，不在这列。无丢包单流 zfstack 大约 3.1–3.5 s/GB，smoltcp-cubic 在跑满的格子上大约 6–12 s/GB。8 条流时 smoltcp 的进程 RSS 到 40 MiB 上下，zfstack 大约 15–30 MiB，kernel 大约 9–17 MiB。这些 RSS 含客户端和模拟器。

## 客户端 sing-box

本机回环，没有额外 RTT，pacing 关闭。和昨天同一台机器上的量级一样。

| 代理 | 下行 1 流 | 下行 8 流 | 上行 1 流 | CPU s/GB | 峰值 RSS | 400 条空闲 |
|---|---:|---:|---:|---:|---:|---|
| zfstack-client | 39.2 Gbps | 33.5 Gbps | 63.1 Gbps | 0.224 | 8.3 MiB | 4.4 KiB/连接 |
| sing-box go | 28.4 Gbps | 26.9 Gbps | 26.7 Gbps | 0.282 | 45.5 MiB | 11.6 KiB/连接 |
| sing-box gvisor | 11.4 Gbps | 27.2 Gbps | 21.9 Gbps | 1.01 | 42.7 MiB | 27.6 KiB/连接 |

direct 单流 60.2 Gbps。加载下的 1 KiB 回显 P99：zfstack 1.33 ms（37.9 Gbps），sing-box go 1.35 ms（28.2 Gbps），gVisor 0.36 ms（10.3 Gbps）。worker 收成 1 个时，zfstack 仍是 39.7 Gbps，gVisor 掉到 4.3 Gbps。

内核没有 `sch_netem`，客户端的 RTT 和丢包这次也没测。lwIP 仍然没有适配器。

## 这轮不能说的

- 默认仍是关。打开需要宿主填入真实下游容量；这里填的是已知 100 Mbps 的 99%。
- 它没有在所有 RTT 上把交互延迟收到基线 RTT。250 ms、多条重连接可以；20/80 ms 只降一段。
- 1% 随机丢包下看不出收益。BBR 的最差 P99 这次没有改善。
- 单流 100 Mbps 没有回退。PR 里数 Gbps、1–2 连接的 −3% 界限这次没有重测。
- 8 秒、多数 1–2 次，不是他们的 12 对 bootstrap。
