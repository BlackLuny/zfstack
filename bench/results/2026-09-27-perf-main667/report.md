## Comparison (zfstack vs kernel / smoltcp, and vs 2026-09-24-full2)

555/555 runs `ok` on isolated TUN (`10.201.0.0/24`, zfstack `940533a` = `main` #667). No correctness failures. Same cell set as [`2026-09-24-full2`](https://github.com/BlackLuny/zfstack/blob/main/bench/results/2026-09-24-full2/report.md) (15 s, 3 reps, RTT 12/80, loss 0/1%, k=2/0.25, 1/8 flows). That archive was a different VM (`tcp_rmem` max 32 MiB, kernel 6.18, default CC bbr); this run is 6 MiB / 6.12 / cubic. Treat full2 as a directional check, not a paired A/B.

**Down goodput**

| Cell | kernel-cubic | smoltcp-cubic | zfstack-cubic | zfstack-bbr |
|---|---|---|---|---|
| 12 ms clean deep, 1 flow | 193 | 192 | **193** (= kernel) | 185 |
| 12 ms clean shallow, 1 flow | 182 | 184 | **187** | 185 |
| 80 ms clean shallow, 1 flow (H1) | 159 | **10.9** (collapse) | **184** | 175 |
| 12 ms 1% deep, 1 flow | 9.4 | 8.0 | 9.8 | **133** |
| 80 ms 1% deep, 8 flows | 12.3 | 12.5 | 13.4 | **132** (smoltcp-bbr 158) |

- CUBIC: zfstack matches kernel on clean deep/8-flow and beats kernel on the 80 ms shallow 1-flow cell where smoltcp-cubic still falls over (10.9 Mbps, same failure mode as full2's 10.4).
- BBR: zfstack keeps line rate under 1% loss at 12 ms; kernel CUBIC does not (expected — client is cubic, server BBR is the difference). smoltcp-bbr is still the unstable stack: many 12 ms cells have 7–10 s zero-throughput and 0.01–0.3× baseline goodput.
- vs full2: headline down cells are unchanged in rank order. `down 80 ms 1% deep 1-flow` zfstack-bbr is 35 Mbps here vs 78 Mbps there, range [15–38] vs [16–80] — high-variance BBR+loss, not a confirmed #667 regression.

**Up goodput**

All five stacks sit on the same CUBIC-client numbers: clean ≈ ceiling, 12 ms 1% ≈ 9 / 73 Mbps, 80 ms 1% ≈ 1.5 / 12 Mbps. zfstack-cubic is a bit behind on 80 ms clean shallow 1-flow (139 vs kernel 144 / smoltcp 159); same cell was 143 vs 189 / 161 in full2. No stall on any stack.

**CPU (stack thread s/effective GB; kernel has no equivalent)**

#667 (right-size initial TX + batch ingress) shows up here:

| Cell | smoltcp-cubic | zfstack-cubic now | zfstack-cubic full2 | zfstack-bbr now | zfstack-bbr full2 |
|---|---|---|---|---|---|
| down 12 ms clean 1 flow | 5.09 | **3.15** | 5.24 | **3.46** | 8.07 |
| down 12 ms clean 8 flow | 6.00 | **3.56** | 5.84 | **4.81** | 10.5 |
| up 12 ms clean 1 flow | 5.20 | 6.24 | 9.38 | 6.15 | 9.27 |

Down CPU is ~40% below smoltcp-cubic and ~40–55% below this tree's full2 zfstack numbers. Upload is still a bit more expensive than smoltcp (receive path), but lower than full2.

**Mixed RR**

- Idle P50 ≈ configured RTT + 0.8 ms on every stack (harness floor).
- Deep queue, loaded: zfstack-bbr stays near idle (P50 12.7 / 80.8 ms). kernel 31 / 117, zfstack-cubic 31 / 155, smoltcp-cubic 27 / 155. Same pacing story as full2; cubic 80 ms P50 improved vs full2's 202 ms.
- Bulk goodput under RR: zfstack-cubic 193/188/193/184; smoltcp-cubic still dies on 80 ms shallow (14 Mbps vs kernel 159 / zfstack 184).

**Connect (2000 / conc 64)**

| | kernel | smoltcp-cubic | zfstack-cubic | zfstack-bbr |

zfstack matches kernel completeness and is slightly tighter on P99. smoltcp listener-pool refusals (H6) are unchanged.

**Not a zfstack defect**

- smoltcp-bbr stalls / multi-minute wall times on shallow or 8-flow down cells (258 s, 617 s observed). Timeout is per-run; the process eventually returned `ok` with near-zero goodput.
- smoltcp-cubic 80 ms shallow collapse is the long-standing H1 cell, not a #667 change.

**Bottom line**

On this isolated 200 Mbps matrix, zfstack-cubic is the kernel CUBIC peer (and the only stack that fills the 80 ms shallow down cell). zfstack-bbr is the latency and lossy-down winner vs kernel CUBIC, and far more stable than smoltcp-bbr. #667 cut zfstack down-path CPU roughly in half versus the September 24 archive without giving up goodput.
